## Allocation and toolchain installation

Allocation `892432` reserved all four V100s on the approved `ault24`:

```bash
salloc --no-shell --immediate=15 --partition=intelv100 --nodelist=ault24 \
  --nodes=1 --exclusive --gres=gpu:4 --mem=128G --time=03:00:00 \
  --job-name=suet-nccl-clean
```

The compute-node checks used `srun --export=NONE --chdir=/tmp` and
`/bin/bash --noprofile --norc`. Shared paths remained absent. This check
removed inherited compiler variables and bypassed compute-shell startup
files; changing `.bashrc` alone did not make the module files accessible.

Module GCC 10.2.0 compiled a probe using C++20 `std::atomic_ref` and concepts
on the login node, and module CUDA 12.1.1's `nvcc` ran there. Those are
partial feature/version checks, not a full module-toolchain stack build.
The newer requested toolchain was installed into a separate scratch prefix
using existing Conda 24.5.0 from `/users/mkhalilo/miniconda3`:

```bash
RETRY=/scratch/mkhalilo/suet-nccl-20261014/retry
CONDA_PKGS_DIRS="$RETRY/conda-pkgs" CONDA_OVERRIDE_CUDA=12.8 \
  /users/mkhalilo/miniconda3/bin/conda create --yes --override-channels \
  -c conda-forge --strict-channel-priority --prefix "$RETRY/toolchain" \
  gcc_linux-64=13 gxx_linux-64=13 cuda-version=12.8 cuda-nvcc=12.8 \
  cuda-cudart-dev=12.8 cuda-cccl=12.8 libhwloc pkg-config make \
  autoconf automake libtool conda-pack cmake ninja

"$RETRY/toolchain/bin/conda-pack" --prefix "$RETRY/toolchain" \
  --dest-prefix /tmp/suet-nccl-retry-mkhalilo-20261014/toolchain \
  --output "$RETRY/toolchain-ault24.tar.gz" --n-threads 8
```

The pack was streamed through Slurm into node-local `/tmp`. Nothing was
installed system-wide, and cluster mounts were not changed. The first
Conda solve requested the wrong package name `hwloc`; the successful
transaction used `libhwloc`.

Conda's CUDA headers/libraries live under `targets/x86_64-linux`. A small
node-local CUDA directory view linked `bin` to the toolchain's `bin`,
`include` to that target include directory, and `lib64` to its target library
directory. This supplied the layout expected by upstream build scripts.
The exact environment is saved in [env.sh](logs/2026-10-14-ault24-retry/env.sh).

The initial build step was bound to logical CPUs `0,32` despite reserving the
node. Its own shell and descendants were later widened to CPUs `0–63`,
without restarting builds or changing sources;
[affinity evidence](logs/2026-10-14-ault24-retry/build-affinity.log) records
the correction. Future launches should request enough CPUs explicitly,
for example `srun --ntasks=1 --cpus-per-task=32 --cpu-bind=cores`, rather
than relying on the default task binding.

Both SUET runs logged `Selected provider is udp;ofi_suet` and
`Using network Libfabric`. GPU P2P and SHM transports were disabled and GDR
was disabled, forcing the SENDRECV host-buffer path. The plugin requests
`FI_ORDER_SAS`, so these runs use ROD on the RUD-capable branch, as approved.
Optional GIN/RMA warnings about RDMA/GDRCopy are not the first failing NET
operation; the logs show that the ordinary Libfabric NET plugin initialized.

## Failure diagnosis and proposed fix — not applied

The 2-GPU run produced four incorrect float values at 8 bytes in both
out-of-place and in-place all-reduce, with errors continuing through 128
bytes. At 256 bytes it connected the tree path and stopped making progress.
The 4-GPU run's first specific error was the OFI connection manager's
`Failed to find callback for id 0`, followed by `Context progress failed: -22`.
Later socket/proxy errors followed that failure. Socket controls and controls
using the same OFI plugin over `tcp;ofi_rxm` passed on both GPU counts.

The addressing defect is independently reproducible through the public
libfabric API. The [standalone probe](diagnostics/endpoint-identity.c)
creates two SUET endpoints in one domain, obtains each name, and inserts both
into an AV. Its output is:

```text
endpoint_0_fi_addr=0
endpoint_1_fi_addr=0
distinct_endpoint_names=YES; address_vector_alias=YES
```

The 52-byte endpoint names differ in their RI. Yet the address vector returns
the same destination handle, so an application cannot select the two
different remote endpoints correctly. Source inspection explains why:

1. [Endpoint naming](../../suet/src/suet_ep.c) includes `pid_on_fep`,
   `start_ri` and the underlying datagram address.
2. [AV insertion](../../suet/src/suet_av.c), lines 87–104, passes only
   `addr->raw_dgram_addr` into the domain peer table and deduplicates on that
   physical peer index. It discards the remote RI/PID from logical AV identity.
3. [SES transmit-header construction](../../suet/src/suet_ses.c),
   lines 1105–1115, stamps `ep->resource_index`, the sender's local RI.
   The receive path selects `domain->ep_table[ses_get_ri(header)]`.
   Therefore local/remote endpoint creation order must accidentally match
   for the packet to reach the intended endpoint.

This is a confirmed endpoint-addressing contract defect and provides a
concrete explanation for failures when the plugin uses several data/CM
endpoints. The controls localize the runtime failure to the SUET path;
a corrected provider has not been built to prove that this is the only
remaining integration issue. The passing one-endpoint-per-process host
tests do not exercise this distinct-endpoint identity requirement.

The proposed fix is to preserve each full remote endpoint identity
`(datagram address, PIDonFEP, RI)` in the logical AV/peer mapping, while
sharing the underlying UDP address as a physical transport resource. Carry
the remote destination identity into TX state and encode its RI in the SES
header. Review stream/receive-context keys consistently. Acceptance should
include distinct AV handles for distinct names, delivery between endpoints
with deliberately different local/remote RIs, mixed data/CM endpoints in a
shared domain, and the original 2-/4-GPU correctness matrix. None of this
provider fix was applied.

An 8-byte Ring-only diagnostic under GDB also failed validation, so forcing
Ring does not cure the data error. The
[completion trace](logs/2026-10-14-ault24-retry/cq-diagnostic-abi.log) is
preserved. The first debugger attempt lacked variable debug information;
the corrected trace used the x86-64 argument/structure layout. The first
standalone probe omitted `fi_cm.h`; only that diagnostic source was corrected.
The corrected probe log is the authoritative identity result.
